## 0. 一页速览（Executive Summary）

| 维度 | 结论 |
|---|---|
| 项目类型 | 个人向「数字花园」PWA + Android 壳 |
| 技术栈 | **零框架**原生 HTML/CSS/ES Module JS + Cloudflare Worker + Cloudflare D1 (SQLite) |
| 构建体系 | **无构建**。没有 bundler、没有 Babel、没有 TS。`www/` 靠 `node scripts/sync-web.js` 复制 |

| 最严重问题 | **3 个核心 JS 文件中文被编码损坏**（`js/api.js`、`js/state.js`、`js/feeds.js`）→ 用户直接看到乱码 |
| 最严重隐患 | Session Token 存 `localStorage`（7 天有效、无法吊销单个会话、无刷新机制） |

## 1. 【业务与核心功能】

**设计模式（真实使用，非套话）**：

1. **晚绑定动作注册表（Late-bound registry）** —— 用可变对象打破 ES Module 循环依赖
   ```js
   // js/actions.js:5-27 —— 全部初始化为 null
   export const actions = { switchView: null, applyRoute: null, ... };
   // js/router.js:245-247 —— 各模块 init 时回填
   actions.switchView = switchView;
   ```
   这是本项目**最核心的架构决策**：因为 `router → weeklies → api → state` 存在环，作者选择用"运行期填空"而不是重构依赖图。副作用是**类型/存在性完全靠约定**，调用处必须写 `actions.foo?.()` 做保护（如 `app.js:77`）。

2. **Hooks / 观察者** —— `bindApiHooks({ onRefresh })`（`js/api.js:16-22`），数据层变更后反向通知 UI 重绘，避免 api.js 依赖具体 UI 模块。

3. **可变单例 state** —— `export const state = {...}`（`js/state.js:40-50`），直接改属性，无 setter/无不可变更新。

4. **IIFE 式模块封装** —— 每个 `initXxx()` 内部定义全部私有函数，只把必要的挂到 `actions` 或 `window`
   - 代价：**缩进风格不统一**。`js/router.js:38` 起的函数体是 4 空格缩进（在 `initRouter` 内），而 `js/router.js:185-241` 的事件绑定缩进回到了 0/4 混合，`app.js:28` 之后甚至出现连续空行（第 42-45、124-125 行）。

## 3. 【UI / 交互规范】

### 3.1 框架与组件库

**结论：100% 手写原生 CSS，无任何 UI 框架/组件库。**

- `index.html` 中**没有** Tailwind / Bootstrap / AntD / Element / Shadcn 的任何引用
- 无 CSS 工具类体系（无 `.flex` / `.p-4` / `.text-lg` 这类原子类）
- **唯一的外部依赖是 DOMPurify**：`index.html:541`
  ```html
  <script src="https://cdn.jsdelivr.net/npm/dompurify@3.1.7/dist/purify.min.js"></script>
  ```

  注释明确其用途："DOMPurify：正文 HTML 白名单清洗，防存储型 XSS"

## 4. 【安全红线与防护策略】

> 整体评价：**这是本项目最出彩的部分**。以下逐项给出实测证据。

### 4.1 鉴权方式（Token / Session）

**方案**：**自研不透明 Session Token（非 JWT、非 OAuth）**

- 登录/注册成功 → `crypto.randomUUID()` 生成 token（`workers/api.js:413, 441`）
- 写入 `sessions` 表，`expires_at = Date.now() + 7 天`（`workers/api.js:414-416`）
- 客户端存 `localStorage['chillin_token']`（`js/state.js:41`），请求时加 `Authorization: Bearer <token>`（`js/api.js:196-198`）
- 服务端校验：`SELECT user_id FROM sessions WHERE token=?1 AND expires_at > ?2`（`workers/api.js:52`）
- 带 **D1 主从同步延迟重试**（60ms 后重查一次，`workers/api.js:56-60`）——细节到位

**密码存储：PBKDF2-SHA256，10 万次迭代，16 字节随机盐**（`workers/api.js:309-321`）
- 格式 `pbkdf2$<iter>$<salt_hex>$<hash_hex>`
- **兼容旧的无盐 SHA-256 并在登录时透明升级**（`workers/api.js:328-331, 436-439`）——迁移设计良好
- 用**时序安全比较** `timingSafeEqualStr` 防时序攻击（`workers/api.js:183-193`）
- 密码强度：≥8 位、≤128 位、必须含字母+数字（`workers/api.js:174-181`）

#### ⚠️ 会话管理的高危点

| 风险 | 证据 | 说明 |
|---|---|---|
| **Token 存 `localStorage`** | `js/state.js:41` | 任一 XSS 即可窃取长期凭证。行业推荐 `HttpOnly` Cookie |
| **7 天不可撤销、无刷新** | `workers/api.js:414` | 无 refresh token、无"登出所有设备"、无密码修改后失效机制 |
| **登出仅删当前 token** | `workers/api.js:795` | 单点登出 |
| **`logout` 中 `authHeader.split(' ')[1]` 无空值保护** | `workers/api.js:793-794` | 若走到这里 `authHeader` 必存在（748 行已闸门），风险低 |
| 过期 session 仅靠 Cron 清理 | `workers/api.js:1472-1480` | 每小时一次，可接受 |

### 4.2 权限校验机制（越权防护）

**核心防线：所有 SQL 都带 `AND user_id = ?`**（实测 `workers/api.js` 各表 GET/PUT/DELETE 均是）。

额外一层**写覆盖防护** `isOwnedRecord`（`workers/api.js:349-354`）：
```js
// 客户端可传 id 触发 INSERT OR REPLACE，写入前校验该 id 是否属于他人
const existing = await db.prepare(`SELECT user_id FROM ${table} WHERE id = ?1`).bind(id).first();
if (!existing) return true;                       // 新记录 → 允许
return Number(existing.user_id) === Number(userId); // 已有 → 必须是本人
```
批量同步 `POST /api/sync/batch` 做了**批量归属校验以消除 N+1**（`workers/api.js:1048-1066` 的 `fetchOwnedSet`），未通过的 item **静默跳过**（`workers/api.js:1071`）。

**文件访问双层控制**：
1. 新文件：URL 必须带匹配的 `?t=<access_token>`（`workers/api.js:457-462`），且用 `timingSafeEqualStr` 比较
2. 历史无 token 文件：要求已登录**且** `user_id` 归属本人，否则 403（`workers/api.js:463-468`）
3. 响应头带 `Cache-Control: private` + `X-Robots-Tag: noindex`（`workers/api.js:488-489`）
4. 注释明确"禁止 UUID 直链 / 302 泄 token"（`workers/api.js:464`）——**说明作者踩过这个坑并修正了**

> 💡 一个残留小问题：`workers/api.js:470-474` 在"登录后访问历史文件"时会给文件补发 `access_token`，但只在**没有传 `?t=`** 时才补发，且用的是 `UPDATE ... WHERE access_token IS NULL`。逻辑正确，但意味着**任何知道 UUID 的登录用户**触发一次补发后，token 就落到他自己手里了——不过 UUID 本身不可猜，可接受。

### 4.4 数据输入校验 / 注入防护

**SQL 注入：实测无风险。** 全仓 SQL 均使用 D1 的**参数化绑定**（`?1, ?2` + `.bind()`）。唯一动态拼接表名/列名的地方均来自**代码内固定常量**，非用户输入：
- `isOwnedRecord(db, table, ...)` —— `table` 由调用方传字面量 `'weeklies'`/`'notes'`/`'bookmarks'`/`'quick_feeds'`（`workers/api.js:351`）
- `fetchOwnedSet(tableName, ...)` —— 同上（`workers/api.js:1052`）
- `scanAndAudit` 的 `tables` 数组 —— 硬编码（`workers/api.js:1704-1709`）

**输入校验现状**：
- `username` 长度 3–32（`workers/api.js:393`）
- `password` 强度（`workers/api.js:174-181`）
- `url` 必须 `^https?://`（`workers/api.js:505`）
- 上传大小 ≤ 5MB（`workers/api.js:766`）
- **URL 路径上的 `:id` 强制数字**：`/api/(weeklies|notes|bookmarks|feeds)/(\d+)`（`workers/api.js:826,880,942,1008`）
- ❌ **但 POST body 里的 `id` 完全不校验类型** —— `workers/api.js:978-990` 仅 `if (body.id)` 就 `.bind(body.id, ...)` 写入主键，无 `Number()`/`Number.isSafeInteger` 断言。这是 §4.5「onclick JS 上下文注入」利用链的一环，**属于本项目的实质输入校验缺口**。
- ❌ 各业务文本字段（`title`/`content`/`category`/`summary`/`tags`）**无长度上限**，仅靠 `body.x || ''` 兜底；而 `weeklies.category/title/summary` 在 schema 中是 `NOT NULL`，客户端漏发会触发 D1 报错 → 返回 500（而非 400）

**上传安全（做得很扎实）**：
- 统一鉴权 + 限流 60/10min（`workers/api.js:754-756`）
- **魔数嗅探优先于 MIME**（`sniffImageMime`，`workers/api.js:195-209`）：手写 JPEG/PNG/GIF/WEBP 签名比对
- 白名单 `image/{jpeg,png,gif,webp}`；**声明类型与嗅探类型不符则 400**（`workers/api.js:772-779`）
- `crypto.randomUUID()` 做文件名 + 独立 `access_token`（`workers/api.js:780-781`）
- 响应强制 `Content-Disposition: inline` + 存 `mime_type`（嗅探值），**不可传 SVG**（SVG 可内嵌脚本，此处已天然规避）
- ❌ 未做图片内容二次编码（原图字节直存 D1），但配合白名单足以防 XSS

**SSRF 防护（超出预期的完备）**：
- `isSafeFetchUrl`（`workers/api.js:268-276`）限定 `http/https` + 拒绝内网主机

### 4.5 XSS 防护

**多层防御，实测有效**：

1. **服务端不返回 HTML** —— 全部走 `jsonResponse`，无字符串拼接 HTML
2. **DOMPurify 清洗富文本** —— `js/utils.js:91-96` `sanitizeHtml()`：DOMPurify 可用则白名单清洗，**不可用则降级为 `escapeHtml`**（fail-safe 设计）。用于正文渲染：`js/weeklies.js:127` `articleBody.innerHTML = sanitizeHtml(finalHtml)`
3. **`escapeHtml` 统一转义**（`js/utils.js:7-15`，含 `& < > " '` 五个字符），实测在 `escapeHtml`/`escapeHtml` 覆盖的渲染点均正确使用
4. **`markdownToHtml` 先转义再格式化**（`js/utils.js:47-88`）—— 注释明确 "Markdown → safe HTML (escape first, then light formatting)"，第 50 行 `escapeHtml(text).split('\n')`。**AI 回复走这条路径**（`js/echo-ai.js:249,263,275`），所以 LLM 输出无法注入 HTML ✅
5. **链接协议白名单**（关键，防 `javascript:`）：
   - `js/bookmarks.js:52-57`
     ```js
     const hasUrl = /^https?:\/\//i.test(rawUrl);
     const card = document.createElement(hasUrl ? 'a' : 'div');
     if (hasUrl) { card.href = rawUrl; card.target='_blank'; card.rel='noopener noreferrer'; }
     ```
     **非 http(s) 时根本不创建 `<a>`**，且带 `rel="noopener noreferrer"`
   - `js/feeds.js:15-25` `extractUrlFromText` 强制 `https://` 补全，且正则本身以 `https?:\/\/` 或裸域名起始
   - `js/feeds.js:141` 自动链接化时，**先 `escapeHtml(contentText)` 再插 `<a href="$1">`**，而 URL 正则字符集 `[a-zA-Z0-9\-._~:/?#[\]@!$&'()*+,;=%]` **不含引号**，无法逃逸属性；`javascript:` 也不匹配 `https?://` 前缀 ✅
6. **CSP**（`_headers:7`）：`default-src 'self'`、`frame-ancestors 'none'`、`base-uri 'self'`、`form-action 'self'`、`object-src` 未显式但被 default-src 覆盖

#### CSP 的两个已知弱点

| 弱点 | 证据 | 影响 |
|---|---|---|
| `script-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net` | `_headers:7` | `'unsafe-inline'` 使内联脚本注入防护失效（项目大量使用内联 `onclick` 与 `<script>`，如 `index.html:15-24, 537-539`，故不得不开） |
| 第三方 CDN 无 SRI | `index.html:541` | DOMPurify 供应链风险 |

**残余 XSS 面（已收敛）**：
- `img src` 来自外部页面的 `og:image`，未做协议校验（`workers/api.js:672-683` 仅把 `http://` 升级为 `https://`）。但 `javascript:` 在 `<img src>` 中不会执行，故不可利用。
- 渲染模板中 `${bm.id}`、`${feed.id}`、`${card.id}` 未转义（如 `js/feeds.js:146,151`、`js/echo-ai.js:31-32`）——见下方专项。

#### 🟠 已确认的真实缺陷：内联 `onclick` 的 JS 上下文注入

**这是本项目唯一已确认的"转义纪律破口"**，且同仓已存在正确写法可对照。

**问题代码**（`id` 直接插入 `onclick` 的 **JavaScript 上下文**，而非 HTML 文本上下文，`escapeHtml` 在此也不适用）：
```js
// js/feeds.js:151
<button class="btn-text text-danger" onclick="deleteFeed(${feed.id})" ...>删除</button>
// js/echo-ai.js:32
<button class="echo-card-delete" onclick="deleteEchoCard(${card.id})" ...>×</button>
```
**正确对照**（同一仓库、同类数据）：
```js
// js/bookmarks.js:78 —— 显式 String() + escapeHtml
<button class="bookmark-card-delete" data-id="${escapeHtml(String(bm.id))}" ...>×</button>
```

**可利用性链（跨前后端闭合）**：
1. 客户端自行生成 id：`js/feeds.js:306` `id: Date.now(),`（**客户端可控**，非服务端自增）
2. 服务端 `POST /api/feeds` **完全不校验 `body.id` 的类型**——实测 `workers/api.js:978-990` 仅 `if (body.id)` 后直接 `.bind(body.id, ...)` 写入 `INSERT OR REPLACE INTO quick_feeds (id, ...)`；**全文件对该字段无 `Number()`/类型断言**。批量同步路径同样：`workers/api.js:1126` `.bind(item.id, ...)`
3. 服务端把原值回显（`workers/api.js:990` `SELECT * ... .bind(body.id, ...)`），客户端存入 `state.feedsDatabase`
4. 重新渲染时 `js/feeds.js:151` 原样插入 `onclick` 属性 → **属性内 JS 语法注入**

注意对比：URL 路径参数**是**强校验数字的（`/api/feeds/(\d+)`，`workers/api.js:1008`），但 **POST body 不是**。

**缓解因素**：需要登录态；CSP 的 `script-src 'unsafe-inline'` 允许内联执行（因此 CSP 不能兜底）；`_headers` 的 CSP **在 Capacitor WebView 内不生效**（`_headers` 是 Cloudflare Pages 专有机制），故 APK 内风险更高。

**修复**：`onclick` 改为 `data-id` + 事件委托（`bookmarks.js` 的做法），并在服务端对 `id` 做 `Number.isSafeInteger` 校验。

### 4.7 🔴 发现的真实缺陷：3 个核心 JS 文件中文编码损坏

**这是本次调研最需要立刻处理的问题。**

**现象**：`js/api.js`、`js/state.js`、`js/feeds.js` 中的**中文字符串与注释全部变成乱码**，例如：
- `js/api.js:85` → `showToast('鐧诲綍宸茶繃鏈燂紝璇烽噸鏂扮櫥褰?, 'warn');`（应为 `登录已过期，请重新登录`）
- `js/state.js:5` → `title: "2023-W42: 璁板繂鍒囩墖"`（应为 `记忆切片`）
- `js/feeds.js:38` → `闅忔墜璁版祦绌虹┖濡備篃`（应为 `随手记流空空如也`）

**根因（已做字节级验证）**：文件内容是经典 **UTF-8 → GBK 误解码** 的产物。验证链：
```
原始正确字符 "登录"  ──UTF-8 bytes──►  E7 99 BB E5 BD 95
                                        │ 按 GBK(936) 解码
                                        ▼
                              鐧诲綍  ──再存为 UTF-8──►  落盘
```
实测 `js\api.js` 偏移 3327 处原始字节为 `E9 90 A7 E8 AF B2 ...`，即字面存着 `鐧诲` 的 UTF-8 编码；而正确的 `登`(U+767B) 的 UTF-8 `E7 99 BB` 在该文件中**出现 0 次**，在未被污染的 `workers/api.js` 中**出现 8 次**。对照实验清晰。

**逆向恢复可行性**：`UTF8字节 → 按GBK取字节 → 按UTF-8解码` 可还原绝大部分文本：
```
恢复结果示例（js/state.js）: "🌸", "2023-W42: 记忆切片", "坂本龙一", "《奥本海默》"
```
但**存在不可逆丢失** —— 原转换过程中部分字符变成了字面 `?`（如 `面。` → `面?`），恢复后表现为 `\uFFFD` 或残留 `?`。

**影响范围（实测精确边界）**：
- ✅ **确认为损坏**：`js/api.js`、`js/state.js`、`js/feeds.js`（乱码特征字符命中 56 / 77 / 14 处）
- ✅ **额外确认（永久性信息丢失）**：`style.css` 有 **22 处** `???` 连续问号，是被彻底损毁的中文注释，且**根目录与 `www/` 两份完全相同**。实例：
  ```css
  /* ????????????????????????*/            /* 原为分区标题 */
  /* ???????????????????Tab ?????? */      /* 原为底部 Tab 注释 */
  /* ????????????READER & BOOKSHELF STYLES ????????????*/
  ```
  **注意**：这类损坏是**不可逆**的（真 0x3F 字节，非显示问题 —— 已字节级确认），与下方 JS 的"可逆向恢复乱码"性质不同，只能重写。
- ✅ **确认干净**：`index.html`、`app.js`、`workers/api.js`、`sw.js`、`functions/api/[[path]].js`、`js/utils.js`、`js/router.js`、`js/weeklies.js`、`js/notes.js`、`js/bookmarks.js`、`js/echo-ai.js`、`js/reader.js`、`js/search.js`、`js/upload.js`、`js/pwa-update.js`、`js/version.js`、`js/actions.js`、`js/ui.js`
- ⚠️ **`www/` 下的 JS 副本是干净的**（`www/js/api.js` 等 0 处命中）—— 说明 `www/` 是**损坏发生前**同步的旧快照

**具体影响逐条**：
1. **用户可见乱码**：`js/api.js` 的登录/同步 Toast（`:85,87,133,140,150,166-172,212,220,225`）、`js/feeds.js` 的空状态与按钮文案（`:38-39,119,151`）、`js/state.js` 的**全部默认种子数据**（首屏无数据时用户看到乱码示例内容）
2. **`www/` 与根目录行为分裂**：Web 端乱码，但 `npm run sync:web` 会**用乱码版覆盖干净的 `www/`**，从而把乱码带进 Android APK
3. **版本代际分裂（实测）**：`www/js/version.js:2` = **`2.4.21`**，根目录 `js/version.js:2` = **`2.5.1`**；`www/sw.js` 的 `CACHE_NAME` = **`chillin-v41`**，根目录 = **`chillin-v47`**。即：**APK 是旧版（2.4.21），Web 是新版但中文乱码**
4. 代码可读性受损（注释也乱码），后续维护成本上升
5. ⚠️ `sw.js:6-7` 预缓存的 `/app.js?v=2.4.21`、`/style.css?v=2.4.21` **已与 `index.html` 请求的版本不匹配**（`index.html:542` 请求 `?v=2.5.1`）。因 SW 采用网络优先策略而未爆雷，但这批预缓存条目是死重

**建议修复顺序**：
1. **先备份** `js/api.js`、`js/state.js`、`js/feeds.js`
2. 逐文件执行 `UTF8读出 → 按 GBK 取字节 → 按 UTF-8 解码`，人工校对 `?`/`\uFFFD` 处（约 24 / 31 / 11 处）
3. 或更可靠：**以干净的 `www/js/*.js` 为基准回填**，再把根目录**独有的新功能**（`www/js/api.js` 比根目录少 2905 字节，差异含增量同步相关改动）手工合并过去 —— 因为 `www/` 只有 13 处乱码特征，本质上是更早的干净版本
4. 统一编辑器/工具为 UTF-8 无 BOM，并加 `.editorconfig`（`charset = utf-8`）防止复发
5. 修复后**必须**改 `js/version.js` 并同步 `sw.js` 的 `CACHE_NAME` 与 `?v=`，否则 PWA 缓存不会更新
