# 备份、恢复与迁移操作手册

> 本手册面向**会动生产数据**的操作，命令均在仓库根目录执行。
> 恢复链路已在本地库**完整实测**（含「备份 → 丢失 → 恢复」演练）；凡访问远端生产环境的命令，执行前请确认已有备份。

## 0. 风险分级

| 操作 | 目标 | 可逆性 |
| :--- | :--- | :--- |
| `npm test` / `npx wrangler deploy --dry-run` | 只读 | — |
| `npm run backup` | 读远端并落盘 | 只读，安全 |
| `npx wrangler d1 migrations apply DB --remote` | 写远端 schema / 数据 | 取决于迁移内容 |
| `npm run restore -- <file> --yes` | **覆盖远端数据** | 只能靠再恢复一次回退 |

## 1. 备份

    npm run backup                 # 导出远端 D1 → backups/，并推一份到 R2
    npm run backup -- --keep 30    # 保留最近 30 份
    npm run backup -- --no-r2      # 只落本地，不推 R2
    npm run backup -- --local      # 导出本地 dev 库，用于演练恢复流程（不上传 R2）

- 产物是 `backups/` 下的 `chillin-d1-<时间戳>.sql.gz`；`backups/` 已在 `.gitignore`，绝不入库。
- 默认目标是**远端生产库**；`--local` 只用于演练，不会上传 R2。
- 远端导出与 R2 上传需要 Cloudflare 凭证，本手册未代跑（会真实访问生产）。

## 2. 恢复

    # 本地演练（不碰生产）
    npm run restore -- backups/chillin-d1-<时间戳>.sql.gz --local

    # 生产恢复：会覆盖现有数据
    npm run restore -- backups/chillin-d1-<时间戳>.sql.gz --yes

安全闸（已由 [docs.test.mjs](../tests/docs.test.mjs) 固化为门禁）：

- 缺文件参数 → 打印用法并退出 1；
- 指向远端却未加 `--yes` → 打印「确认无误请追加 --yes」并退出 1，**不会执行任何命令**。

### 已实测的完整演练（2026-10-18，本地库）

1. 在本地库建探针表并写入一行；
2. `npm run backup -- --local --keep 999` → 输出 `[backup] exporting DB (local)`，产出快照；
3. `DROP TABLE _drill` 模拟数据丢失；
4. `npm run restore -- <快照> --local` → `restore-exit=0`；
5. 读回探针行 → `"note": "drill-ok"`，数据完整恢复。

结论：gzip 解压、临时文件、`wrangler d1 execute --local`、备份导出这条链路是**通的**，不是「文档里存在」。探针表与演练快照随后已删除。

## 3. 应用迁移

    npx wrangler d1 migrations apply DB --local    # 本地先跑
    npx wrangler d1 migrations list DB --remote    # 看远端哪些还未应用
    npx wrangler d1 migrations apply DB --remote   # 应用到远端

注意：`npm run ship` 会**校验远端迁移是否全部应用**，只要存在未应用迁移就直接中断发布。所以「改完就想发」时，必须先应用迁移。

### 3.1 0023_created_at_cst.sql 专项

目的：把 `weeklies` / `notes` / `bookmarks` 的存量 `created_at` 由 UTC 平移 +8 小时，与 `updated_at`、客户端 `toUpdatedTs` 统一为东八区口径。

- D1 按文件名只执行一次；SQL **故意不做幂等判断**（重复 +8 会错位）。
- 语义已有单测覆盖：[garden.test.mjs](../tests/garden.test.mjs) 造一条「UTC created_at + CST updated_at」的历史行，重放 0023 后断言两者对齐、且 `updated_at` 不被改动。
- 只平移这三张表：`quick_feeds` / `prompts` / `reader_books` / `echo_cards` 的 `created_at` 一直是 CST，移动会反向错位。
- 迁移前的抽查（应看到 `created_at` 比 `updated_at` 早 8 小时）：

      SELECT id, created_at, updated_at FROM weeklies ORDER BY updated_at DESC LIMIT 20;

### 3.2 回滚预案

**不要**无脑 `-8 hours`：迁移之后新写入的行本来就是 CST 口径，再减 8 会反向错位。
回滚只回退「迁移执行时刻之前就已存在」的行：

    UPDATE weeklies  SET created_at = datetime(created_at, '-8 hours')
      WHERE created_at IS NOT NULL AND created_at < '<迁移执行时刻，CST，如 2026-10-18 13:00:00>';
    UPDATE notes     SET created_at = datetime(created_at, '-8 hours')
      WHERE created_at IS NOT NULL AND created_at < '<同上>';
    UPDATE bookmarks SET created_at = datetime(created_at, '-8 hours')
      WHERE created_at IS NOT NULL AND created_at < '<同上>';

### 3.3 推荐执行顺序

1. `npm run backup` —— 先有可恢复的快照；
2. 抽查（3.1 的 SELECT）：确认是 UTC 口径、与 `updated_at` 差 8 小时；
3. `npx wrangler d1 migrations apply DB --local` —— 本地先验证；
4. `npx wrangler d1 migrations apply DB --remote`；
5. 抽查 3 行：`SELECT id, created_at, updated_at FROM weeklies ORDER BY id DESC LIMIT 3;` —— 两者应同口径（不再差 8 小时）；
6. 若结果异常：按 3.2 回滚，或 `npm run restore -- <第 1 步的快照> --yes`。
