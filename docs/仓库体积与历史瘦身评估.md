> 初次评估：2026-10-02（HEAD `v2.5.43`，240 提交）· 复核：2026-10-19（HEAD `bd5e0d7`，`v2.5.106`，340 提交）
> 复核结论：**方案 B 与方案 D 均已落地**，`.git` 从 90.2 MB 降到 **3.3 MB**，证据见 §6。

## 2. 历史里最大的是什么（初次评估时的快照）

| 大小 | 路径 | 说明 |
| ---: | :--- | :--- |
| 66.2 MB | `1我话说到这份上，您差不多该生气了吧？.mp3` | 早期误提交，后被 `.gitignore` 的 `*.mp3` 排除 |
| 18.9 MB | 同名 mp3（另一版本） | 同一文件的两个版本都留在历史里 |
| 9.2 MB | `《诡秘之主》…txt` | 电子书，已被 `*.txt` 排除 |

**约 95 MB（占当时 90 MB 打包体积的绝大部分）来自这 8 个文件**，它们与代码无关，且都已通过 `.gitignore` 阻止再次出现——但 `.gitignore` 只能阻止**未来**提交，无法移除历史。

## 3. 这会造成什么实际成本

* **CI 每次都要克隆 90 MB**（`.github/workflows/ci.yml` 在每次 push/PR 都会 checkout）：比必要体积多出约 80 MB 的下载与解包时间；
* 新设备首次克隆、备份、镜像迁移都要多花同等代价；
* GitHub 单文件硬上限 100 MB（66 MB 的 mp3 未被拒绝，但已在告警区间）。

## 4. 可选方案

| 方案 | 收益 | 代价 / 风险 | 最终状态 |
| :--- | :--- | :--- | :--- |
| **A. 保持现状**（默认） | 零风险 | 每次克隆 ~90 MB | 已放弃 |
| **B. `git filter-repo` 重写历史** | 仓库降到约 **3–5 MB** | 240 个提交哈希全部改变、必须 `push --force`、其他克隆/分支失效、Pages 会重建；需本地与 GitHub 双向确认 | **已执行**（实测 3.3 MB） |
| **C. BFG Repo-Cleaner** | 同 B，命令更简单 | 需装 Java；同样要 force push | 未采用 |
| **D. 让 CI 只取浅克隆** | 不动历史，CI 只拉最近 1 次提交 | 一条 `fetch-depth: 1` 即可，**零破坏**，见效最快 | **已执行** |

## 5. 建议（初次评估提出，均已采纳）

1. **先做 D**（成本最低、立即见效、可随时撤销）：CI 里加 `with: fetch-depth: 1`；
2. 若确实在意克隆体积，再考虑 **B**，且必须满足：
   * 先做异地备份（`git clone --mirror`）；
   * 在协作者确认后执行；
   * 执行后立即验证：`git log` 完整、Pages 部署正常、`npm test` 通过；
3. **不建议**为了体积去改工作区文件——它们已经是忽略状态，删本地文件不影响历史。

## 6. 执行结果复核（2026-10-19）

**方案 B（历史重写）已执行**，证据链：

* `git log --all --oneline -- "*.mp3"` 返回 **0 行**——66.2 MB / 18.9 MB 的 mp3 已不在任何**可达**历史中；
* 全库对象扫描（`git cat-file --batch-all-objects --batch-check`）最大 blob 仅 **300,781 字节（≈294 KB）**；mp3 是不可压缩格式，2.90 MiB 的 pack 根本装不下 66 MB；
* `.git` 实测 3.3 MB，落在 §4 方案 B 预估的 3–5 MB 区间内。

**方案 D（CI 浅克隆）也已执行**：`.github/workflows/ci.yml:31` 已是 `fetch-depth: 1`。
