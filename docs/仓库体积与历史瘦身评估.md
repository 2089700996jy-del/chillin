# 仓库体积与历史瘦身评估

> 评估日期：2026-10-02 · 当前 HEAD：v2.5.43 · 结论：**可选操作，需作者明确授权后再执行**

## 1. 实测数据

| 指标 | 数值 |
| :--- | :--- |
| 提交数 | 240 |
| `.git` 目录 | **90.2 MB**（packed 89.55 MiB，松散对象仅 327 KiB） |
| 历史中 blob 总字节 | 125.8 MB |
| 工作区跟踪文件 | 780 → 移出 vendored 快照后约 73 个 |

## 2. 历史里最大的是什么

| 大小 | 路径 | 说明 |
| ---: | :--- | :--- |
| 66.2 MB | `1我话说到这份上，您差不多该生气了吧？.mp3` | 早期误提交，后被 `.gitignore` 的 `*.mp3` 排除 |
| 18.9 MB | 同名 mp3（另一版本） | 同一文件的两个版本都留在历史里 |
| 9.2 MB | `《诡秘之主》…txt` | 电子书，已被 `*.txt` 排除 |
| 4.1 MB | `images/shaxian_*.jpg` ×4 | 旅行照片，已在后续提交中删除，但 blob 仍在 |
| 0.29 MB | `.agents/skills/konsta-ui-repo/package-lock.json` | 第三方快照（已移出跟踪） |

**约 95 MB（占 90 MB 打包体积的绝大部分）来自这 8 个文件**，它们与代码无关，且都已通过 `.gitignore` 阻止再次出现——但 `.gitignore` 只能阻止**未来**提交，无法移除历史。

## 3. 这会造成什么实际成本

* **CI 每次都要克隆 90 MB**（`.github/workflows/ci.yml` 在每次 push/PR 都会 checkout）：比必要体积多出约 80 MB 的下载与解包时间；
* 新设备首次克隆、备份、镜像迁移都要多花同等代价；
* GitHub 单文件硬上限 100 MB（66 MB 的 mp3 未被拒绝，但已在告警区间）。

## 4. 可选方案

| 方案 | 收益 | 代价 / 风险 |
| :--- | :--- | :--- |
| **A. 保持现状**（默认） | 零风险 | 每次克隆 ~90 MB |
| **B. `git filter-repo` 重写历史** | 仓库降到约 **3–5 MB** | 240 个提交哈希全部改变、必须 `push --force`、其他克隆/分支失效、Pages 会重建；需本地与 GitHub 双向确认 |
| **C. BFG Repo-Cleaner** | 同 B，命令更简单 | 需装 Java；同样要 force push |
| **D. 让 CI 只取浅克隆** | 不动历史，CI 只拉最近 1 次提交 | 一条 `fetch-depth: 1` 即可，**零破坏**，见效最快 |

## 5. 建议

1. **先做 D**（成本最低、立即见效、可随时撤销）：CI 里加 `with: fetch-depth: 1`；
2. 若确实在意克隆体积，再考虑 **B**，且必须满足：
   * 先做异地备份（`git clone --mirror`）；
   * 在协作者确认后执行；
   * 执行后立即验证：`git log` 完整、Pages 部署正常、`npm test` 通过；
3. **不建议**为了体积去改工作区文件——它们已经是忽略状态，删本地文件不影响历史。

> 本次**未执行任何破坏性操作**：只做到「第三方快照移出跟踪 + 写入 .gitignore」。历史重写需作者单独授权。
